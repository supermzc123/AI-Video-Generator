# 批量重新启动与任务控制修复

## 复现与原因

- 新批次引用旧失败任务，但启动只排队 READY，FAILED 原样保留，随后批次立即再次结束。
- 任务页使用结构化 retry 命令，遗漏旧 run 接口的批次恢复逻辑；父编排重试后无法登记子任务。
- 编排步骤记录 started 后遇到明确的 HTTP 拒绝，没有记录失败结果，后续重试被当作结果未知而阻止。
- 前端把任务查询和三个辅助查询绑定；任何辅助查询失败都禁用全部任务按钮。操作锁还依赖后续刷新完成，无超时请求可能长期锁住界面。
- 创建与启动分成两次请求；启动失败遗留草稿，下一次却使用新 ID 创建，导致项目已属于活动批次的冲突。

## 修复行为

- 启动批次先检查失败任务是否允许重试，再恢复失败任务；resume 仍只恢复派发，不隐式重试。
- task-commands、run、redo 共用失败重试与批次恢复逻辑；存在较新的活动批次时不复活旧批次，拒绝重试时不先改变批次状态。
- generation 等边界保留失败任务，同时不复活已取消任务。
- 本地语义处理器明确返回 HTTP 拒绝时持久化失败检查点；后续预算内重试使用新操作 ID。传输中断或未知结果继续要求对账。
- 任务列表独立更新任务与辅助状态；读取超时 10 秒、控制超时 30 秒，操作锁不再等待刷新释放。LLM 长调用不套用这些短超时。
- 草稿有明确启动入口。创建回包丢失或启动失败后复用批次 ID，不重复创建。
- 失败任务保留取消入口；次数用尽、截止时间已过或外部结果未明时显示不可重试原因，不重置执行预算。需要新一轮生成时应显式新建，不能通过重试绕过预算。

- 相邻批次、编排、任务控制和真实调度循环集成测试通过。

- Ruff 与 TypeScript/Vite 构建通过。
